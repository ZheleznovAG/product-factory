# Оптимальность протокола уточнения намерений при вводе «только текст / только аудио»

**Вопрос:** насколько оптимально задумана система выяснения того, что хочет пользователь, когда вход — только текст или аудио (без референсов, без биосенсоров)?

**Кратко:** для «только текст» и «аудио → текст» текущий дизайн **работоспособен**, но **не оптимален**. Ниже — что хорошо, что мешает, и как улучшить.

---

## 1. Что уже хорошо для текст/аудио

- **Вход — текст.** Goal и constraints приходят как строки; аудио предполагается транскрибировать во внешнем слое (gateway/клиент), затем тот же API. Контракт не привязан к голосу.
- **Короткие ответы A/B.** Удобны для голоса («Эй» / «Би») и для чата без длинного набора текста.
- **Фиксированный верхний предел (3–5 вопросов).** Ограничивает длину диалога и время до первого результата (целевые 60–90 сек в протоколе 90s).
- **Схема intent.** Outcome / Experience / Constraints покрывают и технические цели (MVP vs production), и переживание/темп — пригодна и для «каталог-API», и для «хочу что-то расслабляющее».
- **IntentGenerator уже парсит цель.** Есть простой `inferTempo(goal, constraints)` по ключевым словам (urgent, fast, careful, stable) — база для адаптации под ввод есть.

---

## 2. Что неоптимально для «только текст / только аудио»

### 2.1 Один и тот же набор вопросов для любой цели

Сейчас все получают одну и ту же последовательность (MVP vs production → проверки → строгость ограничений → темп → риски). Для цели в духе «API для каталога» это уместно; для «хочу тревожно-красивое для вечера» первый вопрос про MVP/production не по делу.

**Итог:** при только тексте/аудио не используется содержание goal/constraints, чтобы решить, **какой** вопрос задать и в каком порядке. Оптимальнее: выбирать и порядок вопросов из анализа ввода (или LLM).

### 2.2 Нет разбора свободного текста перед вопросами

Goal приходит одной строкой; в intent мы не извлекаем структуру (outcome / experience / constraints) из этой фразы. Даже при явных формулировках («быстро и безопасно») всё равно задаём все 5 A/B.

**Итог:** неоптимально для текст/аудио — лишние вопросы там, где часть полей можно вывести из первого сообщения. Оптимальнее: парсить первый ввод (правила или LLM) → заполнять поля intent → спрашивать только про недостающее.

### 2.3 Раннее завершение (уже реализовано)

В `IntentClarification.nextQuestion()` есть ранний выход: после каждого ответа пересчитывается draft (`updateIntentDraft`), и при достаточной полноте (`confidence` + обязательные поля) протокол завершается после 3+ ответов.

**Итог:** это улучшение уже снижает лишние вопросы для текст/аудио. Дальше можно усиливать качество за счёт более точного извлечения intent из первого ввода.

### 2.4 Короткий свободный ответ (реализовано rule-based)

Теперь ответ принимается не только как `A/B`, но и как короткая фраза. В `IntentClarification` добавлен rule-based маппинг по ключевым словам в текущую ось (`Outcome/Validation/Strictness/Tempo/Risk`) с обновлением полей intent.

При неоднозначном ответе поведение такое:
- один уточняющий вопрос;
- если неоднозначность остаётся, fallback на строгий выбор `A/B`.

**Итог:** для текста и аудио (после ASR) канал обратной связи стал шире без изменения контракта intent.

### 2.5 Аудио только как «текст после транскрипции»

Протокол не описывает: повтор вопроса (TTS), прерывание (barge-in), паузы, «не расслышал». Аудио по сути рассматривается как текст после распознавания. Для голосового сценария не заложены ограничения по длине фраз (короткие подсказки для TTS) и порядок «озвучка вопроса → ответ пользователя».

**Итог:** для «только аудио» дизайн не плохой, но и не заточен под голос (нет явной модели диалога и ошибок распознавания). Оптимальнее: отдельный слой «аудио ↔ текст» (VAD, TTS, повторы) и тот же протокол уточнений поверх текста.

## 3. Рекомендации для оптимальности при текст/аудио

| Направление | Действие |
|-------------|----------|
| **Адаптивные вопросы** | Строить банк/порядок вопросов от цели и ограничений (или от LLM по goal+constraints). Не задавать MVP/production для явно не-продуктовых целей. |
| **Парсинг первого ввода** | Перед вопросами: из goal (+ constraints) извлекать outcome/experience/constraints (правила или LLM). Заполнять черновик intent; задавать только про недостающие/неясные поля. |
| **Раннее завершение** | Ввести `nextQuestion(goal, constraints, previousAnswers, currentIntentDraft)`. После каждого ответа обновлять draft; возвращать `null`, если confidence достаточен или обязательные поля заполнены. |
| **Свободный ответ** | Разрешить ответ не только A/B, но и короткую фразу (1–2 предложения). Маппинг в поля intent (правила или LLM); при неоднозначности — один уточняющий вопрос или fallback на A/B. |
| **Аудио-слой** | Явно описать: транскрипция → текст → тот же протокол; при необходимости — TTS для вопросов, политика повторов и таймаутов. Не менять контракт intent; аудио остаётся на границе «ввод/вывод». |

---

## 4. Вывод

Для сценариев **«только текст»** и **«только аудио (как текст после транскрипции)»** система уточнения работоспособна; часть оптимизаций уже внедрена, но потенциал улучшений остаётся:

- Не используется содержание первого ввода для выбора и порядка вопросов.
- Нет парсинга свободного текста в поля intent до вопросов.
- Раннее завершение после 3 вопросов уже есть.
- Поддержка короткой фразы уже есть (rule-based + уточнение/fallback A/B).
- Аудио не выделено в отдельный диалоговый слой (TTS, повторы, прерывания).

Оптимальность достигается за счёт: **адаптивных вопросов по goal/constraints**, **парсинга первого ввода в intent** и **раннего выхода** при достаточной полноте, плюс опционально **свободный короткий ответ** и явный **аудио-слой**. Контракт intent и идея «3–5 A/B» остаются; меняется логика выбора вопросов и момент остановки.

## 5. Архитектурное правило для аудио-слоя

- Канонический pipeline для голоса: `ASR -> текст -> Intent Clarification (3-5 вопросов) -> TTS`.
- `ASR` отвечает за преобразование речи пользователя в текстовый ввод (`goal/constraints/answers`).
- Протокол уточнения не ветвится для аудио: используется тот же текстовый engine и тот же контракт intent.
- `TTS` используется для озвучивания уточняющих вопросов и финального резюме/черновика intent.
- Политики повторов, таймаутов и обработки «не расслышал» живут в аудио-адаптере, а не в core-логике intent.

### 5.0 Рекомендуемый протокол уточнения для audio-only

1. Пользователь формулирует цель голосом; `ASR` выдаёт транскрипт и confidence.
2. При низком confidence аудио-слой делает короткий `TTS`-переспрос (ядро intent не обновляется).
3. Подтверждённый транскрипт обрабатывается тем же `nextQuestion(...)`/`updateIntentDraft(...)`, что и в текстовом режиме.
4. Каждый следующий вопрос формулируется коротко (одна мысль, A/B) и озвучивается через `TTS`.
5. При `barge-in` текущая озвучка прерывается, после чего цикл начинается заново с нового аудио-ввода.
6. Финальный черновик intent озвучивается и при необходимости подтверждается голосом/кнопкой.

### 5.1 Минимальная операционная модель (audio-only)

1. `ASR` принимает реплику пользователя и возвращает транскрипт + confidence.
2. Если confidence ниже порога, аудио-слой делает `TTS`-переспрос (без записи ответа в intent).
3. Подтверждённый текст передаётся в тот же `nextQuestion(...) / updateIntentDraft(...)`.
4. Полученный вопрос/итог озвучивается через `TTS` короткой формулировкой.
5. При `barge-in` текущая озвучка прерывается, новый ввод снова проходит через шаги 1-4.

### 5.2 Критерии качества аудио-слоя

- Не расширять контракт intent аудио-специфичными полями: аудио остаётся boundary-адаптером.
- Ограничивать количество повторов и использовать fallback на явный `A/B`, чтобы удерживать целевой диалог 60-90 секунд.
- Предпочитать edge-first для сырого аудио; в core передавать транскрипт и служебный статус диалога.
