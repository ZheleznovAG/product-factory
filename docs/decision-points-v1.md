# Decision points v1

Фаза 1. Пороговые условия для пересмотра архитектурных решений. Конкретные пороги и триггеры — для MVP. Обновлять при изменении нагрузки, требований или инцидентов.

**Статус:** Active (MVP). Каждый TBD заменён измеримым порогом, триггером пересмотра и стратегией деградации/отката.

---

## 1. Run cost envelope

### 1.1 Жёсткие лимиты (enforced)

Каждый run определяет или наследует:

- `max_llm_tokens_total`
- `max_llm_calls`
- `max_tool_calls`
- `max_wall_clock_seconds`

**Лимиты по умолчанию для MVP:**

| Параметр | Значение |
|----------|----------|
| max_llm_calls | 20 |
| max_llm_tokens_total | 150 000 |
| max_tool_calls | 30 |
| max_wall_clock_seconds | 3600 (1 ч) |

Run прерывается при превышении лимитов.

### 1.2 Целевая стоимость (фаза наблюдения)

Мягкие цели (без жёсткого enforcement, только audit + метрики):

- **< $0.50** на S-класс run
- **< $2** на M-класс run

### 1.3 Триггеры пересмотра (LLM: API → self-host)

| Триггер | Порог | Метрика |
|---------|--------|---------|
| Стоимость | >20% S-run превышают $1 в среднем за 7 дней | ежемесячный отчёт / дашборд |
| Стоимость | LLM cost >70% общей стоимости инфраструктуры | cost breakdown |
| Budget abort | Прерывания по бюджету в >15% run | audit |

**Действие:** обновить ADR, оценить миграцию на self-host (vLLM и т.п.) или другой API.

Дополнительно: суверенность данных, латентность p99, контроль версий модели — см. исходные триггеры в истории документа.

## 2. Latency SLO (LLM и pipeline)

### 2.1 Цели по латентности LLM

**Planner:**

- p95 < 10 s, p99 < 20 s
- Timeout: 30 s

**Codegen:**

- p95 < 30 s, p99 < 60 s
- Timeout: 120 s

Ретраи: макс. 2 с exponential backoff. Circuit breaker: при p99 > 60 s в течение 24 ч — деградация контекста или уменьшение модели.

### 2.2 Классы длительности run (cycle time)

| Класс | Целевое время |
|-------|----------------|
| **S (Small)** | < 30 мин |
| **M (Medium)** | < 2 ч |
| **L (Large)** | < 8 ч (ночной) |

**Цель PRD:** 80% S-run завершаются за < 30 минут. 95% M-run — за < 2 ч.

### 2.3 Триггеры пересмотра

- >30% S-run превышают 45 мин.
- Медианное время run удваивается после добавления фичи.
- Латентность LLM >50% общего времени run.

## 3. RAG: pgvector → выделенная vector DB

**Позиция MVP:** RAG опционален и **выключен по умолчанию** в MVP.

### 3.1 Пороги использования pgvector

Продолжать использовать pgvector пока:

- docs_count ≤ 200 000
- объём векторного хранилища ≤ 10 GB
- p99 retrieval ≤ 500 ms

### 3.2 Tripwire (триггер миграции)

Рассмотреть выделенную vector DB (Qdrant/Weaviate и т.д.) если:

- p99 retrieval > 700 ms в течение 3 дней подряд
- векторное хранилище > 15 GB
- пропускная способность инжеста ниже требуемой в течение 24 ч

### 3.3 SLA поиска RAG

- p95 < 200 ms, p99 < 500 ms
- Жёсткий timeout: 1 s
- Fallback: при сбое retrieval — keyword search или режим без RAG

## 4. Workflow: stub → durable engine (Temporal / аналог)

**Текущее решение:** синхронный workflow-stub в коде фабрики (см. ADR-0001).

**Триггеры пересмотра:**

| Триггер | Порог |
|---------|--------|
| Нагрузка | 50+ прогонов фабрики в день |
| Функциональность | потребность в pause/resume и human-in-the-loop в прод-контуре |
| Инциденты | ретраи/дублирование side-effects приводят к инцидентам; стоимость инцидентов превышает стоимость внедрения durable engine |

---

## 5. Наблюдаемость: файловый audit log → OTLP/backend

**Текущее решение:** файловый audit log (JSONL); OTel в коде есть, экспорт в backend — по необходимости.

**Триггеры пересмотра:**

| Триггер | Порог |
|---------|--------|
| Расследование | невозможность оперативно искать по runId/eventType без OTLP/backend |
| Ретеншн/комплаенс | требование централизованного хранения с политикой retention (см. ADR-0005) |
| Масштаб | несколько инстансов фабрики или рост объёма событий |

---

## 6. Телеметрия и retention (сводка)

- **Audit:** 90 дней online, 1 год cold (ADR-0005). Alert: рост > 50 GB/мес или один run > 10 MB audit.
- **Application logs:** 30 дней.
- **LLM prompt/response:** по умолчанию только метаданные (hash, token count, duration, cost); полное хранение — по явному флагу.

---

## 7. Новые tools с side-effects

Правило без изменений: каждый новый инструмент с side-effects перед добавлением в реестр требует threat model, обновление OPA, при risk tier privileged — human approval и decision log.

## 8. Пересмотр документа

- При срабатывании триггера — инициировать ADR или обновить существующий.
- Еженедельно — просмотр метрик; ежемесячно — архитектурный пересмотр.
- Раз в квартал (или при изменении risk register) — проверить актуальность порогов.
