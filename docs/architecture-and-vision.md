# Архитектура и путь к целевой системе

Один документ, чтобы понимать: что за система сейчас, почему она «маленькая», и как из неё прийти к целевой «крутой» системе.

---

## 1. Что у нас сейчас (и почему так)

**Сейчас это действительно маленькая система с ограничениями — и это намеренно.**

Мы строим не «сразу всё», а **управляемое ядро**, которое потом обрастает возможностями. Идея из [system-audit-corrective-plan.md](system-audit-corrective-plan.md) и [strategic-fork-factory-2.md](strategic-fork-factory-2.md): если ядро выполнения не формализовано, агентный слой превращается в хаос; поэтому **сначала стабильность, потом интеллект**.

| Слой | Сейчас | Ограничение |
|------|--------|-------------|
| **Вход** | goal + constraints + target_stack | Пять YAML-контрактов опциональны (FACTORY_CONTRACTS_DIR). Нет самообслуживания «из коробки». |
| **Планировщик / кодоген** | LLM при NEURAL_SERVICE_URL, иначе stub | Генерируют план и patch sets, но **патчи не применяются** к репо — только в audit. Реальный артефакт = копия архетипа. |
| **Артефакт** | Копия одного из архетипов (catalog-service, web-app) | Архетипы **создаём мы вручную**. Новый тип продукта = новый архетип в репо. |
| **Куда попадает результат** | workspace/ в контейнере; при настройке — S3/MinIO (ZIP) | Нет push в Git, нет создания репо в GitHub/GitLab «из коробки». |
| **Оркестрация** | Один процесс, state machine в памяти | Нет Temporal: нет долгих прогонов с паузой/ретраем «из коробки». |

Итого: **это контролируемая «маленькая» система** — детерминированное ядро (state machine, policy, tool executor, audit), плюс опциональный LLM для плана и предложений по коду, плюс один реальный side-effect (копия архетипа и при желании загрузка в S3). Ограничения не «забыли», а **выбрали как первый шаг**, чтобы не размазывать ответственность и не давать агенту прямой доступ к Git/деплою без инструментов и политик.

## 2. Целевая «крутая» система (куда мы идём)

В документах это описано как **Factory 2.0** и дальше. Кратко — к чему стремимся:

- **Пользователь** описывает цель (и при желании контракты) → получает **готовый репозиторий в Git** (или ссылку на артефакт в хранилище), прогнанный CI и при необходимости деплой в staging.
- **Планировщик и кодоген** реально влияют на результат: план используется для выбора шагов и инструментов; предложения по коду (патчи) **применяются** к репо через tool, а не только пишутся в audit.
- **Инструменты:** не только «скопировать архетип» и «загрузить в S3», но и **создать репо в GitHub/GitLab**, **push**, **запуск CI**, при необходимости **деплой в staging** — всё через Tool Executor и политики (approval где нужно).
- **Масштаб и надёжность:** при росте — durable engine (Temporal), SLO/cost, RAG для контекста, полноценный AI-risk и supply chain.

То есть «крутая система» — это та же **архитектура** (Control Plane vs Intelligence Plane, side-effects только через tools, audit, policy), но с **расширенным набором инструментов и сценариев**, с применением патчей от кодогена и с интеграциями (Git, хранилища, CI, деплой). Мы не меняем принцип «маленькой управляемой системы» — мы **наращиваем её возможности** внутри тех же границ.

## 3. Так и надо: текущая архитектура — правильный шаг

Да, **так и надо**. Текущая архитектура не «урезанная по ошибке», а **осознанный первый этап**:

1. **Границы слоёв** ([ADR-0002](adr/0002-layer-boundaries.md)): агент только генерирует предложения; все side-effects — через Tool Executor. Это остаётся и в «крутой» системе.
2. **Один образ, один рантайм (JVM)** — без Node/Python в рантайме фабрики. Это остаётся.
3. **Контракты, политики, audit** — основа для масштабирования и комплаенса. Они же будут использоваться при добавлении Git, apply patch, деплоя.
4. **Опциональный LLM и опциональное хранилище (S3)** — фабрика работает и без них; при включении не ломается детерминированное ядро.

Путь к «крутой» системе не «переписать всё», а **добавлять по шагам**:

- Tool «создать репо в Git + push» (и при необходимости approval).
- Tool «применить patch» по предложениям кодогена (с политикой и audit).
- Дальше — CI trigger, деплой в staging, при росте — Temporal, RAG, SLO/cost.

Всё это уже **заложено в документах**: [strategic-fork-factory-2.md](strategic-fork-factory-2.md), [whats-next.md](whats-next.md), [integrations-server-deployment.md](integrations-server-deployment.md), [tools-list-mvp.md](tools-list-mvp.md). Текущая «маленькая» система — та же архитектура, с минимальным набором tools и без части интеграций; целевая — та же архитектура с полным набором.

## 4. Краткая схема «сейчас → цель»

```
СЕЙЧАС (маленькая система)                    ЦЕЛЬ (крутая система)
─────────────────────────                    ─────────────────────

Запрос (goal, target_stack)                  То же + самообслуживание при необходимости
        ↓                                              ↓
Planner (LLM или stub) → план в audit        Planner → план используется для шагов
        ↓                                              ↓
Codegen (LLM или stub) → patch в audit      Codegen → patch применяется (tool apply_patch)
        ↓                                              ↓
Tool: copy archetype → workspace/            Tools: copy archetype, create Git repo, push,
        ↓                                     apply patch, trigger CI, deploy staging
Опционально: upload в S3                    Артефакт в Git + CI + при необходимости S3/деплой
        ↓                                              ↓
Результат: путь или s3://…                  Результат: URL репо, статус CI, ссылка на артефакт
```

Принцип один: **Control Plane (workflow, policy, tools, audit) не меняется по сути**; добавляются инструменты и интеграции, и всё так же идёт через контракты и политики.
