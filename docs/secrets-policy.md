# Политика секретов

Фаза 2. Как хранить и передавать секреты (API-ключи LLM, токены Git/CI, credentials облака). Детали инфраструктуры — в [ADR-0001](adr/0001-stack-and-prerequisites.md).

## Принципы

- Секреты **не хранятся** в коде и не коммитятся в репозиторий.
- Секреты **не логируются** и не попадают в трейсы/метрики; при необходимости — redaction в логах.
- Доступ к секретам — только для компонентов, которым они нужны по роли (Gateway, Workflow, Tool Executor, CI).
- Ротация ключей — по политике организации; при утечке — немедленная ротация и аудит.

## Реализация для MVP

- **MVP:** Вариант A — Kubernetes Secrets и/или переменные окружения ([ADR-0006](adr/0006-secrets-management-mvp.md)); абстракция SecretsProvider для последующей миграции на Vault.
- **Post-MVP:** централизованное хранилище (HashiCorp Vault или аналог) при необходимости ротации, изоляции по тенантам или комплаенса.

## Какие секреты

- Ключ/токен LLM API (OpenAI или совместимый).
- Токен доступа к Git (создание репо, коммиты).
- Credentials для CI (запуск pipeline, статусы).
- Credentials для деплоя (K8s, облако) — при появлении деплой-tool.
- Секреты создаваемых продуктов — не в фабрике; только механизм подстановки (например, из Vault по пути) при генерации манифестов.

## Пересмотр

При переходе на multi-tenancy или усиленных требованиях к изоляции — ввести per-tenant или per-run scope секретов и обновить этот документ.
