# Монолит и выделяемые сервисы

Кратко: что у нас в одном процессе, что уже вынесено наружу и что можно поднять отдельно (в т.ч. в Docker).

---

## 1. Сейчас — один процесс (монолит)

**Фабрика** — один JVM-процесс (один образ, один контейнер). Внутри него в одном процессе:

| Компонент | Где живёт | Внешняя зависимость |
|-----------|-----------|----------------------|
| HTTP API (Ktor) | тот же процесс | — |
| Workflow, state machine | тот же процесс | — |
| Audit log | тот же процесс (файл или память) | опционально — путь на volume |
| Approval store | тот же процесс (файл) | опционально — путь на volume |
| Artifact registry | тот же процесс (файл) | опционально — путь на volume |
| Tool Executor (create_repo, S3 upload) | тот же процесс | S3/MinIO по HTTP (внешний сервис) |
| Policy (OPA) | вызов по HTTP | **OPA — отдельный сервис** (OPA_URL) |
| Neural (LLM) | вызов по HTTP | **Neural gateway / API — отдельный сервис** (NEURAL_SERVICE_URL) |
| Контракты, валидатор | тот же процесс | только файлы/директории |

Итого: **логически монолит** (всё в одном приложении), но **уже зависит от внешних сервисов** — OPA и нейросервис опционально, S3/MinIO при включённой загрузке артефактов. Эти сервисы можно поднимать в Docker рядом с фабрикой.

---

## 2. Что уже можно выделить (отдельные сервисы в Docker)

| Сервис | Назначение | Админка / UI |
|--------|------------|--------------|
| **MinIO (или любой S3)** | S3-совместимое хранилище артефактов | MinIO Console (порт 9001) |
| **OPA** | Policy engine (allow/deny, require approval) | Нет встроенной UI; есть OPA Playground отдельно |
| **Neural gateway** | Единая точка для LLM (Codex/OpenAI/proxy) | Нет; проверка через /health |
| **Фабрика** | Наше приложение | Нет админки; API + health |

Всё это можно поднять в одном docker-compose: фабрика, MinIO (с консолью), OPA, neural-gateway. Пример — в deploy/docker-compose.yml.

---

## 3. Что можно выделить позже (не обязательно сейчас)

- **Audit log** — вынести в отдельный сервис (например Kafka + consumer в БД или object storage). Сейчас файл/volume достаточно.
- **Approval store** — вынести в API/БД. Сейчас файловое хранилище.
- **Артефакт-реестр** — вынести в БД или объектное хранилище. Сейчас файлы в директории.

Это не обязательно для «крутой» системы; выделение имеет смысл при масштабировании (несколько инстансов фабрики, централизованный аудит).

---

## 4. Итог

- **Монолит** — да, одно приложение в одном контейнере.
- **Внешние сервисы уже есть:** OPA, нейросервис, S3/MinIO — всё вызывается по HTTP/API, их можно поднимать в Docker параллельно с фабрикой.
- **Админки:** MinIO Console — из коробки (порт 9001); для OPA/фабрики при желании добавить позже (например простой UI для approvals).

Полный пример стека в Docker: [deploy/docker-compose.yml](../deploy/docker-compose.yml) и [deploy/README.md](../deploy/README.md). В compose: фабрика, MinIO (S3-совместимое хранилище), OPA, опционально neural-gateway (profile `with-neural`).

---

## 5. Нужно ли дробить на отдельные сервисы сейчас?

**Нет.** Текущее разбиение достаточное для масштаба и целей (solo, MVP/Scale закрыты). Логика в [solution_design.md](solution_design.md) и [architecture-and-vision.md](architecture-and-vision.md): Control Plane (workflow, policy, tools, audit) в одном процессе — осознанный выбор; LLM и OPA уже вынесены по HTTP.

| Вопрос | Ответ |
|--------|--------|
| **Делить ли API, Workflow и Tool Executor на три сервиса?** | Нет. Они тесно связаны (один run = цепочка API → workflow → policy → planner/codegen → tools → audit). Разделение даст только сетевые вызовы и усложнение без выигрыша при одном инстансе. |
| **Выносить ли Audit / Approvals / Artifact Registry в отдельный сервис?** | Не сейчас. Имеет смысл при **нескольких инстансах фабрики** (общий audit/approvals) или при необходимости централизованного UI/запросов по логам. Тогда — Kafka + consumer в БД или object storage, либо отдельный Audit API. |
| **Главный кандидат на выделение в «другой сервис»?** | **Workflow engine (Temporal или аналог).** В roadmap уже есть: durable execution, ретраи, паузы. Тогда фабрика станет **API + воркеры**, а оркестрация шагов живёт в Temporal. Граница естественная: «кто решает, что делать» — в Temporal; «кто выполняет шаг» (tool, LLM вызов) — наш код. |
| **Отдельный сервис «Tool Executor» с секретами?** | Теоретически можно изолировать side-effects в отдельном процессе с минимальными правами. Для текущего масштаба избыточно: секреты и так через env/секреты, выполнение в том же процессе проще отлаживать и трассировать. |

**Итог:** оставляем один процесс фабрики (API + workflow + tools + audit/approvals/registry в памяти/файлах). Внешние сервисы — OPA, нейросервис, S3 — уже вынесены. Следующий шаг по архитектуре — **подключить Temporal** (или аналог), а не дробить монолит на множество микросервисов.
