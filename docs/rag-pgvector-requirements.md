# Требования к RAG + pgvector для Product Factory

## Контекст и цель

Документ фиксирует **требования и варианты реализации** RAG-подсистемы для Product Factory без написания кода.

Целевое назначение RAG:

- поиск релевантных фрагментов по `archetypes/` (шаблоны, runbook, CI/CD заготовки);
- поиск по документации в `docs/` (ADR, политики, roadmap, how-to);
- поиск по артефактам прошлых factory run (audit, результаты, решения, ретроспектива).

Связь с планом работ: фаза 4 содержит задачу `Настроить RAG ingestion + pgvector, версионирование индекса` в [phases-task-list.md](/Users/zheleznov/research/ProductFactory/docs/phases-task-list.md).

## Область действия

- Только требования к данным, хранению индекса, версиям и операционным сценариям.
- Только варианты архитектуры (с trade-off), без выбора финального дизайна.
- Без изменений runtime-стека в Docker-образе фабрики.

## Функциональные требования

1. RAG должен поддерживать поиск по трём источникам: `archetypes/`, `docs/`, history прошлых run.
2. Для каждого найденного фрагмента обязателен provenance:
   - источник (путь/идентификатор run);
   - версия источника (commit SHA, run id, timestamp);
   - версия индекса.
3. Поиск должен быть воспроизводимым: одинаковый запрос + одинаковая версия индекса дают тот же набор кандидатов (с учётом детерминированной конфигурации retrieval).
4. Должен существовать механизм переиндексации при изменениях в `archetypes/` и `docs/`.
5. Должен существовать механизм безопасного rollback на предыдущую версию индекса.

## Варианты хранения индекса

### Вариант A: pgvector в основном Postgres фабрики

- Единая БД для operational-данных и vector-индекса.
- Плюсы:
  - меньше инфраструктурной сложности;
  - проще бэкап/restore и observability в одном контуре.
- Минусы:
  - конкуренция за ресурсы с транзакционными workload фабрики;
  - риск влияния RAG-нагрузки на latency основного API.

### Вариант B: отдельный Postgres + pgvector

- Выделенный экземпляр Postgres для индекса.
- Плюсы:
  - изоляция производительности и отказов;
  - независимое масштабирование/тюнинг.
- Минусы:
  - дополнительная операционная сложность (доступы, бэкапы, мониторинг, сеть).

### Вариант C: отдельный vector-сервис (внешний движок)

- Индекс вынесен в специализированный сервис.
- Плюсы:
  - специализированные возможности по ANN/масштабированию.
- Минусы:
  - новый технологический контур и интеграционный риск;
  - может конфликтовать с ограничением на минимальный runtime-футпринт фабрики.

## Версионирование индекса

Минимальные требования:

1. Версия индекса должна быть явной сущностью (`index_version_id`) и попадать в audit.
2. Для `archetypes/` и `docs/` версия должна быть привязана к commit SHA репозитория.
3. Для данных прошлых run версия должна учитывать watermark по run id/time range.
4. Нужны два режима обновления:
   - incremental (добавление/обновление изменённых документов);
   - full rebuild (полная пересборка при изменении схемы chunking/embedding).
5. Нужна политика совместимости:
   - при изменении модели эмбеддингов создаётся новая версия индекса;
   - старые версии хранятся ограниченное время по retention-политике.
6. Нужен атомарный promote:
   - build новой версии;
   - валидация;
   - переключение `active_index_version` без частично-обновлённого состояния.

## Нефункциональные требования

- Наблюдаемость: метрики ingestion, freshness, retrieval latency, hit-rate, доля запросов без релевантных совпадений.
- Безопасность: доступ к индексу и исходным документам только в рамках policy/roles фабрики.
- Аудит: логировать, какая версия индекса участвовала в каждом factory run.
- Стоимость: отслеживание storage growth и стоимости переиндексации.

## Ограничения и явные не-цели

- Этот документ **не** включает код, SQL-схемы и конкретные API.
- Этот документ **не** фиксирует выбор одного варианта хранения как окончательный.
- Этот документ **не** меняет текущие layer boundaries (side-effects через Tool Executor, policy/approval остаются обязательными).
