# Карта данных фабрики

Фаза 1. Классификация данных: что обрабатывается, назначение, хранение, PII, retention. Для MVP — минимальный объём; расширяется по мере появления новых компонентов.

## 1. Входные данные (product request)
- **Что:** цель, ограничения, контекст (текст/структура).
- **Назначение:** генерация спецификации и плана агентом.
- **PII:** возможно (если в запросе упоминаются персональные данные). Рекомендация: не включать PII в запросы или маскировать перед логированием.
- **Хранение:** по необходимости — только в рамках одного workflow run; не сохранять в долгоживущее хранилище без политики.
- **Retention:** не дольше, чем требуется для отладки и аудита; по умолчанию 30 дней для логов запросов (см. [ADR-0005](adr/0005-log-audit-trace-retention.md)).

## 2. Артефакты агента (спеки, планы, код)
- **Что:** PRD, ADR, граф задач, сгенерированный код, конфиги.
- **Назначение:** создание репозитория и запуск CI/CD.
- **PII:** обычно нет; при наличии — не логировать фрагменты с PII в трейсы.
- **Хранение:** репозитории (Git); артефакты сборки — в артефакт-хранилище по политике CI.
- **Retention:** по политике репозитория и артефактов (обычно бессрочно для кода, ограничено для артефактов сборки).

## 3. Логи и трейсы
- **Что:** логи приложения, OTel-трейсы, события audit (tool calls, решения policy).
- **Назначение:** отладка, расследование инцидентов, метрики.
- **PII:** не допускать запись секретов и PII в логи; при необходимости — redaction.
- **Хранение:** выбранный backend (Loki, облако и т.д.), см. ADR-0001.
- **Retention:** audit 90 дней online + 1 год cold; application logs и traces 30 дней (см. [ADR-0005](adr/0005-log-audit-trace-retention.md)).

## 4. Секреты и учётные данные
- **Что:** API-ключи LLM, токены доступа к репо/CI, credentials облака.
- **Назначение:** только для исполнения фабрики; не для обучения моделей.
- **Хранение:** для MVP — K8s Secrets или env (см. [ADR-0006](adr/0006-secrets-management-mvp.md)); Vault — post-MVP. Не в коде и не в логах.
- **Retention:** по жизненному циклу ключей; ротация по политике безопасности.

## 5. Eval-датасеты и RAG-индексы (после фаз 5–6)
- **Что:** датасеты для RAGAs, agent missions, security redteam; эмбеддинги и векторный индекс.
- **Назначение:** качество и регрессионные проверки.
- **PII:** датасеты не должны содержать реальные PII без обезличивания.
- **Retention:** версионирование индексов; датасеты — по политике экспериментальных данных.

---

**Обновление:** при добавлении новых источников данных или хранилищ обновить эту карту и при необходимости risk register / data governance.
