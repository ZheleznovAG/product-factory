# Нейросервис: где подключать, как управлять и масштабировать

Сводка по задумке: куда в системе встраивается нейросеть/агент, кто им управляет, как масштабировать и как это контролировать.

---

## 1. Где это в архитектуре

```
[ User ] → [ Factory API ] → [ Workflow ] → [ Policy (OPA) ] → [ Agent Runtime ] → [ LLM / нейросервис ]
                                                                       ↓
                                                              [ Tool Registry ] → [ Tool Executor ]
```

- **Подключение:** нейросервис вызывается **только из Agent Runtime** (планировщик, кодоген). Workflow не ходит в LLM напрямую: он вызывает агента, агент внутри дергает нейросервис по одному API.
- **Где в коде:** точка входа — внедрение `NeuralServiceClient` в те классы, которые реализуют `AgentPlanner` / `AgentCodegen`. Сейчас там stub’ы; при появлении LLM-реализаций они получают клиент с `NEURAL_SERVICE_URL` и делают `chatCompletion(messages)`.
- **Где физически:** фабрика (Kotlin) и нейросервис — **разные процессы**. Фабрика может быть в Docker/ K8s; нейросервис — облачный API (OpenAI, Azure и т.д.), свой шлюз на хосте (`scripts/neural_gateway`), self-hosted (vLLM, Ollama) или роутер (LiteLLM). Связь только по HTTP: один URL + при необходимости ключ.

Итого: **подключается** в конфиге фабрики (`NEURAL_SERVICE_URL`, `NEURAL_SERVICE_API_KEY`); **вызывается** только из агентного слоя; **управляется** снаружи фабрики (свой или чужой сервис).

---

## 2. Где настраивать и управлять

| Что | Где |
|-----|-----|
| **URL и ключ** | Окружение фабрики: `NEURAL_SERVICE_URL`, `NEURAL_SERVICE_API_KEY`. В Docker — env при `docker run` или в compose; в K8s — Secret/ConfigMap. |
| **Выбор модели** | Опционально в клиенте (параметр `model` в запросе). Или на стороне роутера/шлюза: по `model`/заголовку решают, в какой бэкенд слать. |
| **Лимиты и бюджеты** | Не в нейросервисе, а в **фабрике**: OPA + `policies/budgets.yaml`, risk tiers (`docs/risk-tier-mapping.md`). Там задаются max_tokens_per_run, max_tool_calls_per_run, max_wall_clock_seconds. Workflow передаёт в policy текущее потребление; при превышении — deny. |
| **Human approval** | Тоже в фабрике: policy возвращает `require_human_approval` → запрос уходит в ApprovalStore, продолжение только после approve. Нейросервис об этом не знает. |
| **Роутер (несколько фирм/моделей)** | Разворачивается и настраивается **отдельно** от фабрики. Фабрике даётся один URL роутера; кто за ним (OpenAI, Anthropic, свой агент) — решается конфигом роутера. |

Управление «нейронкой» с точки зрения фабрики = конфиг URL/ключ + политики и бюджеты внутри фабрики. Всё остальное (масштаб бэкенда, квоты провайдера, роутинг) — снаружи.

---

## 3. Масштабирование

- **Фабрика (оркестрация):** масштабируется как обычное приложение: несколько реплик за балансировщиком, stateless. Каждый запрос `POST /factory/run` — отдельный run; состояние в state machine и audit log.
- **Нейросервис:** фабрика к нему только ходит по HTTP. Масштабирует его тот, кто им владеет:
  - **Облачный API (OpenAI и т.д.):** масштаб и лимиты на стороне провайдера; у нас только бюджеты в policy и при необходимости rate limit на своей стороне.
  - **Свой шлюз (например `scripts/neural_gateway`):** поднимаете несколько инстансов за балансировщиком или один инстанс с очередью; при росте нагрузки добавляете реплики или переносите на роутер (LiteLLM и т.п.), который уже умеет пулы и ретраи.
  - **Self-hosted (vLLM, Ollama):** масштабирование по правилам этого продукта (реплики, GPU, батчи). Фабрика по-прежнему знает только один URL (или URL роутера перед пулом).

Триггеры пересмотра (см. `docs/decision-points-v1.md`): cost per run растёт → смена провайдера или self-host; latency/нагрузка растёт → масштаб или смена бэкенда. Решения фиксируются в ADR (например ADR-0001).

---

## 4. Управление рисками и затратами

- **Бюджеты:** в policy (OPA) задаются лимиты на run: токены, число вызовов инструментов, wall-clock. Данные для проверки (например оценка токенов по run) передаются в OPA; при превышении — отказ. Так ограничивается и «разгул» нейросервиса в рамках одного run.
- **Approvals:** операции с высоким risk tier (deploy, секреты и т.д.) требуют human approval; это решается в фабрике до/после вызова tools, не в нейросервисе.
- **Наблюдаемость:** OTel-трейсы на run и на шагах (в т.ч. вызов агента/планировщика/кодогена). Cost per run считается по метрикам/логам (токены × цена) и может быть KPI для решений о смене провайдера или self-host (`docs/system-audit-corrective-plan.md`, раздел KPI и бюджет).
- **Eval/trace grading:** при включении — прогоны и оценка качества агентных трасс; регрессия может блокировать продвижение. Это следующий шаг после текущих stub’ов.

Итого: **управлять** нейросервисом в контексте фабрики = задать URL/ключ, выставить политики и бюджеты в фабрике, смотреть метрики и при необходимости менять бэкенд или масштаб снаружи.

---

## 5. Краткая схема

| Вопрос | Ответ |
|--------|--------|
| Где подключать? | В конфиге фабрики: `NEURAL_SERVICE_URL` (и при необходимости ключ). Вызов только из Agent Runtime (планировщик/кодоген). |
| Кто управляет? | URL/ключ — оператор фабрики. Бюджеты и approvals — policy в фабрике (OPA, risk tiers). Роутер и сам бэкенд — кто его развернул. |
| Как масштабировать? | Фабрика — реплики/балансировщик. Нейросервис — масштабируется отдельно (провайдер, свой шлюз, self-host); фабрика только дергает один URL. |
| Как ограничивать затраты/риски? | Бюджеты в policy, human approval для high-risk, метрики cost per run и trace grading (когда будут). |
