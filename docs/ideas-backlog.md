# Backlog идей развития

Идеи из планировщика (мозговой штурм, улучшения, рефакторинг).

---

- Добавить `dry-run` режим для Tool Executor с детальным планом side-effects (что было бы выполнено, с какими параметрами и почему policy пропускает/блокирует шаг), чтобы безопасно отлаживать пайплайны до реального запуска.
- Ввести "Contract Drift Guard": автоматическое сравнение входных YAML и `contracts/schemas/*.schema.json` с генерацией отчёта о несовместимостях и рекомендациями по миграции (`apiVersion`, обязательные поля, deprecations).
- Реализовать автогенерацию ADR-черновика из результатов спринта (контекст, принятые решения, альтернативы, риски, последствия) с привязкой к `docs/risk-register.md` и статусом approvals.
- Добавить `golden scenarios` для ключевых archetype-потоков (валидный прогон, отказ policy, rollback), чтобы каждый релиз фабрики проверял предсказуемость решений Planner и Codegen на фиксированных входах.
- Ввести `policy simulation dashboard`: сводку по срабатываниям approvals/блокировок по risk-tier и типам действий Tool Executor, чтобы быстро видеть узкие места в governance и корректировать правила.
- Реализовать версионирование output-артефактов фабрики (`manifest + provenance + checksum`) с проверкой воспроизводимости между запусками одинакового набора 5 YAML-контрактов.
- Добавить `LLM fallback matrix`: конфиг приоритетов и таймаутов для нескольких OpenAI-совместимых провайдеров (`primary/secondary`), чтобы Planner/Codegen автоматически продолжали работу при деградации основного `NEURAL_SERVICE_URL`.
- Ввести `SLO gate` перед выпуском артефакта: автоматическая проверка целевых метрик качества (время генерации, доля policy-deny, процент успешных прогонов golden smoke) с блокировкой релиза при выходе за пороги `quality_profile`.
- Реализовать каталог "reference products" (эталонные наборы 5 YAML + ожидаемые outputs) для быстрого регресса и сравнения изменений в стратегиях Planner между версиями Factory 1.x/2.x.
- Добавить `explain plan`-отчёт от Planner в формате "требование -> выбранное решение -> компромисс -> затронутый риск", чтобы пользователю было проще аудитировать причины каждого шага генерации.
- Ввести `budget-aware execution`: лимиты по токенам/времени/стоимости на прогон с ранним предупреждением и автоматическим понижением режима (например, компактные промпты и укороченный цикл рефлексии) при приближении к порогу.
- Реализовать post-run `contract patch suggestions`: после неуспешного прогона фабрика предлагает минимальные правки входных YAML (в diff-формате) для прохождения валидации и policy без ручного перебора.
