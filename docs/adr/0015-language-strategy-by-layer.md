# ADR-0015: Языковая стратегия по слоям (polyglot)

**Дата:** 2026-02-27  
**Статус:** accepted  
**Контекст:** выбор языков по слоям системы Intent→Reality Engine без жёсткой привязки к одному стеку; возможность масштабирования и смены технологий.

## Контекст

Control Plane уже реализован на Kotlin/Ktor (API, workflow, tool executor, policy, audit). Нужно явно зафиксировать: где оставляем Kotlin, где целесообразны другие языки (runner, eval, UI), чтобы не «жениться» на одном языке везде и сохранить возможность переключения технологий.

## Решение

**Polyglot по слоям:**

| Слой | Язык/стек | Обоснование |
|------|------------|--------------|
| **Control Plane** (API, orchestration, governance) | **Kotlin + Ktor** | Уже реализовано; ближайшие критические задачи — AuthN/AuthZ, budgets enforcement, fail-closed — быстрее закрыть в текущем стеке. Высокая плотность кода, типизация, контракты/DSL. |
| **Tool Runner / Sandbox / Remote Executor** | **Go** (или Rust при необходимости максимальной изоляции) | Один бинарник, простой деплой, изоляция, контроль ресурсов. Не тащить JVM в раннеры. |
| **Intelligence / Evals / Data science** | **Python** | Офлайн-эвал, датасеты, метрики, эксперименты — дешевле и быстрее в Python. Отдельно от execution core. |
| **UI / Portal / Decision console** | **TypeScript** (React/Next) | Админка, портал runs/approvals/artifacts — быстрее на TS; не грузить API слой UI-логикой. |
| **Политики** | **Rego** (OPA) | Policy-as-code уже через OPA; без изменений. |

**Инвариант:** контракты и протоколы остаются язык-нейтральными (JSON Schema, OpenAPI, tool protocol, audit event schema, policy input). Тогда смена языка в одном слое = «переписали один сервис», а не перелом всей системы.

**Триггер пересмотра Kotlin в Control Plane:** потребность в очень лёгком control-plane (минимальный footprint, быстрые старты), унификация языка с runner’ами или сильная команда по Go — тогда рассмотреть миграцию ядра на Go. До закрытия security hardening (AuthN/AuthZ, budgets, fail-closed) миграция ядра не рекомендуется.

## Альтернативы

- **Kotlin везде:** раннеры и eval на JVM — тяжелее операционно, сложнее изоляция.
- **Go для Control Plane сейчас:** перенос работающего кода отложит закрытие критичных пробелов по безопасности.
- **Rust для ядра:** максимальная строгость, но скорость разработки и сложность команды; для orchestration-ядра чаще избыточно.

## Последствия

- **Плюсы:** ядро остаётся в Kotlin до стабилизации; раннеры и UI можно развивать на Go/TS без переписывания ядра; контракты позволяют менять реализацию по слоям.
- **Минусы:** несколько языков в репо — нужна явная документация (этот ADR) и конвенции по границам.
- **Смягчение:** границы слоёв и контракты описаны в architecture-and-path, solution_design; planning pipeline учитывает этот ADR при генерации плана технологий.

## Триггеры пересмотра

- Завершён security hardening и появилась целевая причина переносить Control Plane на Go.
- Решение внедрить Rust для раннеров (изоляция/безопасность).
- Изменение границ слоёв (например, перенос части логики из ядра в runner).
