# ADR-0001: Стек и external prerequisites

**Дата:** 2026-02-19  
**Статус:** принят (proposed для обсуждения)  
**Контекст:** выбор технологий и перечень внешних зависимостей для MVP Product Factory в режиме solo.

## Контекст

Фабрика строится одним разработчиком с опорой на агентов. Нужно зафиксировать: (1) ключевые технологические решения для MVP, (2) перечень внешних зависимостей (prerequisites), без которых нельзя начать фазу 3–4.

## Решение

### Стек (рекомендуемый для MVP, можно заменить по обстоятельствам)

| Компонент | Вариант для MVP | Альтернативы |
|-----------|------------------|--------------|
| Workflow / оркестрация | Temporal Cloud или self-host Temporal | Argo Workflows (для batch-ориентированных сценариев) |
| Политики | OPA (Rego) | — |
| LLM | OpenAI API (или совместимый) | Self-host vLLM при требованиях к суверенности |
| Репозитории | Git (GitHub / GitLab) | Любой Git-хостинг |
| CI | GitHub Actions / GitLab CI | Любой CI с возможностью запуска тестов и деплоя |
| Деплой в staging | Argo CD + K8s или аналог | Простой деплой (Docker Compose, PaaS) для самого первого MVP |
| Наблюдаемость | OpenTelemetry + backend (traces) | Логи/трейсы в облачный сервис провайдера |
| Секреты | Переменные окружения / облачный secrets manager | HashiCorp Vault при росте |

Выбор «cloud-first» для MVP снижает операционную нагрузку; интерфейсы (OTel, OpenAI-compatible API, S3-compatible storage) сохраняем для возможной миграции.

### External prerequisites (обязательные перед фазой 3–4)

1. **Репозиторий** для кода фабрики и (при необходимости) для архетипов и окружений. Доступ на запись из CI и из фабрики (token/key).
2. **CI** с возможностью: запуск тестов, сборка артефактов, вызов скриптов (например, quality_gates). Доступ к секретам (ключи API, токены).
3. **Среда staging** для деплоя создаваемых продуктов (K8s namespace, PaaS stage, или один сервер с контейнерами).
4. **Механизм секретов:** хранение API-ключей LLM, токенов доступа к Git/CI; передача в фабрику и CI без записи в код/логи.
5. **Хранилище логов/трейсов:** куда отправлять OTel-сигналы (или файловые логи с ротацией) для отладки и аудита.
6. **Реестр артефактов** (опционально для самого первого MVP): для образов и SBOM после внедрения supply chain (фаза 6).

### Не решено в этом ADR (отложено)

- Конкретный облачный провайдер (AWS/GCP/Azure) или on-prem.
- Версии инструментов (Temporal, OPA, Argo CD).
- Детальная политика retention для логов и audit.

## Последствия

- **Плюсы:** единая точка фиксации решений; понятный список зависимостей для подготовки окружения.
- **Минусы:** смена стека потребует обновления ADR и возможной доработки интеграций.
- **Смягчение:** при смене компонента обновить этот ADR и документировать миграцию.

## Триггеры пересмотра

- Требования к суверенности данных / он-прем.
- Рост стоимости LLM или CI и необходимость смены провайдера.
- Добавление второй команды или multi-tenancy.
